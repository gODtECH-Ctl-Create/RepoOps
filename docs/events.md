# Operational events — schema version 1

`src/core/events.mjs` defines the public in-process contract for future producers
and consumers. It performs no GitHub calls, logging, persistence, or mutations.
An event is an immutable fact; #24's mutable progress receipt remains a recovery
journal. A pending or ambiguous receipt is never proof of a completed action.
#20 will emit audit records; #21/#36 will build history projections.

## Envelope

Every listed field is required. Unknown fields are rejected at every level.

| Field | Contract |
|---|---|
| `schemaVersion` | Integer `1` |
| `id` | Derived `roe1_` + SHA-256 hex; generated by the constructor, checked by validator |
| `type` | Supported event type from the table below |
| `timestamp` | Original occurrence time, explicit UTC ISO 8601; canonical output includes milliseconds |
| `repository` | `{ id, fullName }`: positive safe integer GitHub ID and owner/repo snapshot |
| `actor` | `{ kind, id }`: user/bot with positive numeric ID, or system with null ID |
| `resource` | `{ type, id, number }`: issue/pull_request, GitHub numeric ID and repository-local number |
| `source` | Discriminated source defined below |
| `metadata` | Exact type-specific fields from the table below; never a raw payload bag |

The actor identifies the initiating account when known, not automatically the
bot that executed the write. Scheduled policy actions may use the system actor.
Do not substitute a username for a missing numeric identity. IDs outside JS's
safe-integer range fail rather than silently losing precision.

RepoOps source: `{ kind: "repoops", operationKey, occurrence }`. `operationKey`
is the trusted 64-character lowercase SHA-256 key from the operation layer.
`occurrence` is a positive stable producer ordinal: use 1 for a single completed
fact, or a documented action/attempt ordinal for distinct diagnostic occurrences.
Do not increment it just because delivery repeats. Producers must persist/reuse
identity and occurrence time; freshly calling Date.now on replay is incorrect.

GitHub source: `{ kind: "github", eventName, action, eventId }`. `eventId` is the
positive numeric GitHub timeline/event identity, not text extracted from a body.
Source event/action must match the GitHub type below. A future adapter must
verify provenance and, for merged PR observations, confirm actual merge evidence.
Validation alone cannot authenticate caller-supplied values. Delivery UUID-based
adapters need an explicit future schema decision; do not coerce UUIDs to numbers.

## Types and metadata

| Type | Resource | Metadata / source rule |
|---|---|---|
| `issue.claimed` | issue | `assigneeId` |
| `issue.unclaimed` | issue | `assigneeId` |
| `issue.blocked` | issue | `reasonCode`: dependency, maintainer, external, other |
| `assignment.reminder_sent` | issue | `assigneeId`, `assignmentEventId`, `window`, `reminderAfterDays` |
| `assignment.expired` | issue | `assigneeId`, `assignmentEventId`, `expireAfterDays` |
| `pull_request.state_changed` | pull_request | `from`, `to`: distinct normalized queue states |
| `operation.failed` | issue or pull_request | `action`, `reasonCode` |
| `operation.ambiguous` | issue or pull_request | `action`, `reasonCode` |
| `github.issue.assigned` | issue | `assigneeId`; source issues/assigned |
| `github.issue.unassigned` | issue | `assigneeId`; source issues/unassigned |
| `github.issue.closed` | issue | empty object; source issues/closed |
| `github.pull_request.merged` | pull_request | empty object; source pull_request/closed with merge confirmed by producer |

All numeric metadata is positive safe integers; day intervals are 1–36500.
Queue states: waiting-for-ci, waiting-for-author, waiting-for-review,
changes-requested, blocked, ready-for-maintainer, unknown. These are schema
vocabulary for #12; this module does not classify PRs.

Diagnostic actions: claim, unclaim, block, remind, expire, classify-pr.
Only classify-pr uses a pull_request resource. Failed reason codes:
github-api-error, invalid-state, invalid-configuration, permission-denied, unknown.
Ambiguous codes: unknown-mutation-result, conflicting-evidence, malformed-receipt.
A failure or ambiguity is a separate event, never a successful claimed/reminder fact.

Blocked/expired/state-change types define future contracts; they do not implement
those capabilities or authorize automatic release. All non-github types require
a repoops source. A GitHub assignment observation is not automatically a RepoOps
claim; preserve that distinction even when both refer to the same mutation.

## Identity, replay and append semantics

`createOperationalEvent(facts)` validates required facts, canonicalizes the time,
derives identity and deep-freezes a detached copy. `validateOperationalEvent`
accepts a complete JSON record and checks its ID as well as its schema.

Identity hashes `[schemaVersion, type, repository.id, resource.type, resource.id,
source]` using canonical object-key ordering. Names, metadata and timestamps do
not supply operation identity. The same identity must have the same full facts:
a changed actor, timestamp, repository-name snapshot or metadata is a conflict,
not a new event or an overwrite. Preserve original snapshots when replaying.

`appendOperationalEvent(history, event)` is a pure reference helper: it validates
all records, preserves input order, returns a new frozen array, deduplicates exact
replays, and raises EventConflictError for conflicting identities. It does not
mutate input history or sort late arrivals by timestamp. Duplicate entries in an
input history are normalized under the same rules. A future durable sink must
provide its own atomic append/uniqueness guarantee; this is not an event store.
Corrections and later observations must be distinct source occurrences/events,
with a reviewed schema if new relationship fields are needed.

## Compatibility and privacy

Unknown versions/types fail explicitly. Consumers must surface or quarantine
unsupported events, never pretend they were successfully consumed. Schema changes
require documented producer/consumer compatibility and migration tests; strict v1
readers cannot assume future fields/types are safe. Never rewrite original records
in place to migrate an append-only history.

Metadata allowlists intentionally exclude issue titles/bodies, free-form blocker
reasons, emails, raw webhook payloads, headers, tokens and API error bodies. Numeric
account IDs are retained only for operational attribution. Error messages include
fixed field paths, not supplied values. Allowlisting is not authentication or a
semantic secret scanner: trusted adapters must supply the correct typed facts.

## Example

```js
import { createOperationalEvent, appendOperationalEvent } from '../src/core/events.mjs';
import { operationKey } from '../src/core/idempotency.mjs';

const event = createOperationalEvent({
  schemaVersion: 1,
  type: 'issue.claimed',
  timestamp: '2026-09-16T00:00:00Z',
  repository: { id: 10, fullName: 'owner/repo' },
  actor: { kind: 'user', id: 30 },
  resource: { type: 'issue', id: 20, number: 19 },
  source: {
    kind: 'repoops', occurrence: 1,
    operationKey: operationKey({ repositoryId: 10, issueId: 20,
      event: 'issue_comment', action: 'created', sourceId: 40 })
  },
  metadata: { assigneeId: 30 }
});
const history = appendOperationalEvent([], event);
```

The IDs/time above are deterministic examples, not claims of live activity.
Run `npm run check` for schema, privacy, replay and conflict regression tests.
